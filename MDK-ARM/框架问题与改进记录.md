# 框架设计问题记录

本文档用于记录当前 BSP 框架中值得改进的设计，作为后续重构和评审的参考。

## 1. 定时器周期回调只支持一组注册

### 当前实现

`bsp_tim.c` 使用两个文件级静态变量保存定时器句柄和周期回调函数：

```c
static TIM_HandleTypeDef *s_period_htim;
static bsp_tim_period_callback_t s_period_callback;
```

注册函数直接覆盖这两个变量：

```c
void bsp_tim_reg_callback(TIM_HandleTypeDef *htim,
                          bsp_tim_period_callback_t callback)
{
    s_period_htim = htim;
    s_period_callback = callback;
}
```

### 存在的问题

该设计在整个定时器 BSP 模块中只能保存一组“定时器句柄 + 回调函数”。如果多个模块依次注册不同定时器，后一次注册会覆盖前一次注册。

例如：

```c
bsp_tim_reg_callback(&htim2, tim2_callback);
bsp_tim_reg_callback(&htim3, tim3_callback);
```

第二次调用后，模块中只保留 `htim3` 和 `tim3_callback`，`htim2` 的回调将无法再通过该机制触发。

因此，这个接口并不是“每个定时器各自只能注册一个回调”，而是“整个 BSP 定时器模块总共只能注册一个定时器的一个回调”。接口名称和参数形式容易使使用者误以为它支持多个定时器。

### 可能造成的影响

- 多个定时器使用周期中断时，先注册的回调会悄悄失效。
- 注册函数没有返回错误，调用方无法发现旧回调已被覆盖。
- 不同业务模块都调用注册函数时，会产生隐蔽的模块冲突。
- 后续增加定时器功能时，需要修改底层实现，扩展性较差。

### 改进建议

使用回调注册表保存多组定时器和回调函数的对应关系：

```c
typedef struct
{
    TIM_HandleTypeDef *htim;
    bsp_tim_period_callback_t callback;
} bsp_tim_callback_entry_t;

#define BSP_TIM_MAX_CALLBACKS  8U

static bsp_tim_callback_entry_t s_period_callbacks[BSP_TIM_MAX_CALLBACKS];
```

注册时根据 `htim` 查找已有项目或空闲位置：

- 同一个定时器重复注册时，更新它自己的回调。
- 不同定时器注册时，使用不同的表项。
- 注册表已满时，返回失败状态，不能静默覆盖其他定时器。
- 可以允许传入 `NULL`，用于注销指定定时器的回调。

回调触发时，根据 HAL 传入的 `htim` 查找对应表项，再调用相应的回调函数。

建议将注册函数改为带返回值的接口，例如：

```c
bool bsp_tim_reg_callback(TIM_HandleTypeDef *htim,
                          bsp_tim_period_callback_t callback);
```

这样调用方可以得知参数无效、注册表已满等情况。

### 临时使用约束

在完成重构前，应明确规定该接口只能由一个定时器使用，并避免多个业务模块重复调用 `bsp_tim_reg_callback()`。

## 2. UART 中断处理函数重复调用 HAL

### 当前实现

`bsp_uart_irq_handler()` 在处理完框架自定义的 UART 空闲事件后，会继续调用 HAL 的通用 UART 中断处理函数：

```c
void bsp_uart_irq_handler(UART_HandleTypeDef *huart)
{
    uint8_t i;

    if (!huart) {
        return;
    }

    if (bsp_uart_is_idle(huart)) {
        for (i = 0U; i < s_rx_idle_callback_count; i++) {
            if (s_rx_idle_callbacks[i].huart == huart
                && s_rx_idle_callbacks[i].callback) {
                s_rx_idle_callbacks[i].callback(huart);
                break;
            }
        }
    }

    HAL_UART_IRQHandler(huart);
}
```

该函数内部调用一次 `HAL_UART_IRQHandler()` 是合理的，因为它可以作为 UART 中断的完整封装：先分发 BSP 的 IDLE 回调，再让 HAL 处理发送、接收和错误等其他 UART 中断。

但当前 `USART3_IRQHandler()` 和 `USART6_IRQHandler()` 在调用 `bsp_uart_irq_handler()` 后，又调用了一次 `HAL_UART_IRQHandler()`。其结构相当于：

```c
void USART3_IRQHandler(void)
{
    bsp_uart_irq_handler(&huart3);  // 内部已经调用HAL_UART_IRQHandler
    HAL_UART_IRQHandler(&huart3);  // 再次调用
}
```

因此，同一次 UART 硬件中断会连续执行两次 HAL 中断处理函数。

### 存在的问题

- 重复执行 HAL 中断处理逻辑，增加中断占用时间。
- 第一次处理可能已经清除标志位、改变 UART 状态或关闭相关中断，第二次处理的行为不直观。
- 中断入口和 BSP 封装之间的职责边界不清晰，后续维护时容易继续产生重复调用。
- 多数情况下第二次调用可能因为标志已经被处理而不执行有效操作，但代码不应依赖这种结果。

### 改进建议

建议让 `bsp_uart_irq_handler()` 作为完整的 UART 中断封装，并在硬件中断入口中只调用它一次：

```c
void USART3_IRQHandler(void)
{
    bsp_uart_irq_handler(&huart3);
}

void USART6_IRQHandler(void)
{
    bsp_uart_irq_handler(&huart6);
}
```

保留 `bsp_uart_irq_handler()` 内部的：

```c
HAL_UART_IRQHandler(huart);
```

这样中断处理顺序保持为：

```text
USARTx_IRQHandler
    -> bsp_uart_irq_handler
        -> 分发BSP的IDLE回调
        -> HAL_UART_IRQHandler处理其余UART事件
```

此外，USART1 当前只调用 `HAL_UART_IRQHandler(&huart1)`，没有经过 `bsp_uart_irq_handler()`。如果 USART1 以后也需要使用 BSP 的 IDLE 回调机制，应将它统一接入相同的封装入口。

## 3. 蜂鸣器驱动中的函数指针注释术语错误

### 当前注释

`drv_buzzer.c` 中三个变量的类型都是函数指针，但注释将其写成了“指针函数”：

```c
static drv_buzzer_set_fn_t  s_set;      // 设置开关的指针函数
static drv_buzzer_freq_fn_t s_set_freq; // 设置频率的指针函数
static drv_buzzer_duty_fn_t s_set_duty; // 设置占空比的指针函数
```

### 存在的问题

“函数指针”和“指针函数”不是同一个概念：

```c
void (*func)(uint8_t);  // 函数指针：变量中保存函数地址
uint8_t *func(void);    // 返回指针的函数，常被称为指针函数
```

`s_set`、`s_set_freq` 和 `s_set_duty` 用于保存底层硬件控制函数的地址，所以它们都是函数指针变量。当前注释的术语顺序错误，容易让阅读者误解变量类型。

该问题不会影响编译和程序运行，属于注释准确性与代码可读性问题。

### 改进建议

将注释改为：

```c
static drv_buzzer_set_fn_t  s_set;      // 蜂鸣器开关控制函数指针
static drv_buzzer_freq_fn_t s_set_freq; // 蜂鸣器频率设置函数指针
static drv_buzzer_duty_fn_t s_set_duty; // 蜂鸣器占空比设置函数指针
```

项目中的相关注释应统一使用“函数指针”这一规范术语。

## 4. DBUS 接收残帧时仍可能保留旧数据的有效状态

### 当前实现

`drv_dbus_port_uart_idle_handler()` 在 UART 产生空闲中断后停止 DMA，并读取 DMA 剩余接收数量：

```c
remain = bsp_uart_get_rx_dma_remain(huart);

if (remain == 0U) {
    drv_dbus_decode(s_port_buffer, &decoded);

    /* 数据范围校验 */

    if (is_valid) {
        s_port_data = decoded;
    }
    s_port_is_valid = is_valid;
}

(void)bsp_uart_rx_dma(huart, s_port_buffer, sizeof(s_port_buffer));
```

只有 DMA 收满整个缓冲区，即 `remain == 0U` 时，代码才会解析数据并更新 `s_port_is_valid`。

### 存在的问题

如果发送过程在一帧中间停止，UART 在空闲达到一帧时间后会触发 IDLE 中断。此时 DMA 尚未收满，`remain` 不为 0，代码会丢弃本次残帧并重新启动 DMA，但不会把 `s_port_is_valid` 清零。

例如：

```text
上一帧完整且有效：s_port_is_valid = 1
下一帧只收到部分数据：remain != 0
当前代码跳过解析：s_port_is_valid仍然为1
```

上层可能继续读取上一帧的旧数据，并把它误认为当前仍然有效。对于遥控器输入，这可能导致通信异常后控制量不能及时失效。

此外，代码通过 `(void)` 忽略了重新启动 DMA 的返回值。如果 `bsp_uart_rx_dma()` 返回 `HAL_BUSY` 或 `HAL_ERROR`，接收可能已经停止，但状态仍可能保持有效。

### 改进建议

残帧出现时应明确将 DBUS 状态标记为无效，并检查 DMA 重新启动的结果：

```c
if (remain == 0U) {
    /* 解析、校验并更新数据 */
    s_port_is_valid = is_valid;
} else {
    s_port_is_valid = 0U;
}

if (bsp_uart_rx_dma(huart, s_port_buffer,
                    sizeof(s_port_buffer)) != HAL_OK) {
    s_port_is_valid = 0U;
}
```

还可以由上层增加接收超时机制：只有在规定时间内持续收到有效 DBUS 帧时才允许使用遥控器数据，超过超时时间后立即将输入判定为离线。

## 5. 缺少键鼠输入到机器人控制目标的完整链路

### 当前实现

当前应用层支持 DBUS 遥控器控制和 CAN 上位机控制，并非只有遥控器控制。

`app_gimbal_comm_dbus_rx()` 使用遥控器的摇杆、拨轮和开关生成控制输入，并通过 S2 选择遥控器、CAN 上位机或急停。CAN 接收接口则接收底盘速度、云台角度和发射机构等已经转换好的控制指令。

底层 `drv_dbus_decode()` 已解析 DBUS 数据中的 `mouse` 和 `keyboard` 字段，但当前 `app_gimbal_comm` 和哨兵控制代码没有使用这些字段生成控制目标。已有字段解析不等于已经具备完整的键鼠控制功能，也不能视为官方图传键鼠接收接口的实现。

### 存在的问题

当前缺少从键鼠输入到控制目标的映射，例如 WASD 到底盘目标速度、鼠标移动到云台角度增量、鼠标按键到发射机构控制请求。因此，仅有键鼠数据或接入官方传输信道，仍不能直接通过键鼠控制本项目中的机器人。

官方信道负责传输输入数据，机器人程序仍需实现对应的接收解析、输入映射和控制源选择。项目现有的 CAN 上位机指令接口使用自定义报文格式，不能直接代替官方键鼠协议的接收接口。

### 改进建议

- 明确键鼠数据来源：使用 DBUS 中的键鼠字段，或接入官方图传键鼠接口；根据实际设备和协议版本实现接收解析。
- 增加键鼠输入处理模块，将按键和鼠标数据转换为底盘、云台和发射机构控制目标，复用现有控制算法和电机输出接口。
- 明确遥控器、键鼠、CAN 上位机之间的控制源切换规则，避免多个输入源同时修改控制目标。
- 为键鼠输入增加有效状态、接收超时和失效处理；切换控制源时处理残留目标及按键状态。
- 核对所用协议版本的字段、字节序、按键位定义和数据单位，避免直接混用 DBUS 与官方图传协议的解析方式。

### 临时使用约束

在补齐上述链路前，应将当前功能描述为“支持遥控器与 CAN 上位机控制，尚未实现完整键鼠控制”，不能仅凭驱动已解析键鼠字段就宣称支持键鼠操作。
